Cascading prompts, three ways

Users start broad and narrow in: pick a value of a top-level attribute and only the related values of the next attribute down appear — then the next, and the next. Each choice decides what you can pick next. This guide covers four ways to build that in classic Strategy BI, each with a live example from the MicroStrategy Tutorial demo project and its own trade-offs. Approach 1 · the prompt-in-prompt pattern

1Nested prompts

The classic prompt-in-prompt pattern (KB10434): each level is an element-list prompt plus a filter that wraps it, and the next prompt's element list is restricted by the previous filter. It filters the SQL itself, so only the chosen slice ever leaves the warehouse. Here it is live — answer Category and click next, and the Subcategory list arrives already narrowed:

Cascading Prompts Demo (Category - Subcategory - Item)live

Embedded live from Strategy Library — you've already been signed in to the demo, so it runs with no login prompt. Frame not loading? See embedding & documentation.

Flow diagram: how the objects connect

Each level is a pair of objects; only the deepest filter goes on the report, and the engine discovers the rest of the chain from there. No depth limit.

+Pros

  • Filters the SQL itself — only the chosen slice is retrieved, so it scales to very large dimensions.
  • Works on reports, and flows into subscriptions and bursting.
  • Guided, one-question-at-a-time experience for the user.
  • No depth limit — stack as many levels as the business needs.

−Cons

  • Two objects to build per level, and the Workstation editor gap needs the placeholder-swap workaround.
  • Lives on reports — on a dashboard it prompts once per dataset, not per viewer interaction.
  • Every level should be Required, or nothing filters (see gotchas).
On a dashboard — and the distinction that leads to approach 2

Wrap this prompted report in a dashboard and the cascade is answered once, when the dashboard opens (decided per dataset) — not per viewer interaction. For always-on narrowing inside a dashboard, use targeted filters — approach 2, next.

Approach 2 · the dashboard-native route

2Targeted filter panel

On a dashboard, cascading is a built-in feature of the filter panel: an attribute filter can target other attribute filters, so a selection in Category instantly narrows what the Subcategory filter offers. No prompt objects, no wizard. Here it is live — pick a Category in the panel and watch Subcategory and Item narrow:

Cascading Filter Panel - Category, Subcategory, Itemlive

The three filters — Category, Subcategory, Item — target each other down the chain, and the grid updates as you go. If the filter panel is collapsed, open it from the dashboard toolbar.

+Pros

  • Native dashboard feature — no custom objects, just Select Targets.
  • Instant on an in-memory cube: every narrow is answered from memory, no re-query.
  • Per-viewer and always on — the interaction Library users already expect.

−Cons

  • Only filters data already in the dataset — the dataset must hold the full domain.
  • On a live-connect dataset each interaction fires SQL (fine for small lookups, heavier for big ones).
  • Dashboard-only — not available for scheduled reports or bursting.

Approach 3 · the one-object shortcut

3Hierarchy prompt

One prompt instead of a chain: a hierarchy qualification prompt on the Products drill hierarchy gives users a tree picker — expand Electronics, see its subcategories, qualify at any level. The cascade comes free from the hierarchy definition. This dashboard runs on exactly that:

Cascading Prompt - Product Hierarchy Promptlive

+Pros

  • One object — fastest to build, no filter chain, and no Workstation gap.
  • Users can qualify at any level: a whole category, or individual items.
  • Filters the SQL like nested prompts, so it scales the same way.

−Cons

  • A tree picker, not a guided step-by-step wizard.
  • Needs a clean drill hierarchy to already exist in the schema.
  • "Qualify anywhere" can confuse less-technical users; the optional-prompt trap still applies (this demo's prompt is optional, so skipping it returns all products).

Approach 4 · automation

4REST API

The same cascade, driven by the public REST API instead of the UI — ideal for provisioning many cascades at once or scripting a migration, and there's no editor gap because there's no preview step. Two parts: at run time the API answers the prompts one level at a time (below), and at build time the API creates the object chain (the recipe). Public Modeling API, one changeset per object, committed in order because each object must exist before the next references it:

# per level: prompt, then the filter that wraps it
POST /api/model/changesets?schemaEdit=false        → X-MSTR-MS-Changeset header

POST /api/model/prompts
{ "information": { "subType": "prompt_elements", "name": "Elements of Subcategory (cascading)", "destinationFolderId": "…" },
  "question": { "attribute": { "objectId": "<Subcategory>", "subType": "attribute" },
                "listAllElements": false,
                "filter": { "objectId": "<Category Filter Prompted>", "subType": "filter" } },   ← the cascade; no preview, no error
  "restriction": { "required": true, "allowPersonalAnswers": "none" } }

POST /api/model/filters
{ "information": { "subType": "filter", "name": "Subcategory Filter Prompted", "destinationFolderId": "…" },
  "qualification": { "tree": { "type": "predicate_element_list",
    "predicateTree": { "elementsPrompt": { "objectId": "<subcategory prompt>", "subType": "prompt_elements" } } } } }

POST /api/model/changesets/{id}/commit   {}

# the report — reference the deepest filter (the spec's "standaloneFilter" shape is rejected; use this)
POST /api/model/reports
{ "sourceType": "normal",
  "dataSource": { "dataTemplate": { "units": [ Category, Subcategory, Item, {metrics: [Revenue]} ] },
    "filter": { "tree": { "type": "predicate_filter_qualification",
      "predicateTree": { "filter": { "objectId": "<Item Filter Prompted>", "subType": "filter" }, "isIndependent": 0 } } } },
  "grid": { "viewTemplate": { … } } }
POST /api/model/reports/{id}/instances/saveAs      → X-MSTR-MS-Instance header from the create

Two traps found while building this live: resolve attributes from the system hierarchy, not name search (search can return managed attribute twins with the same display name that prompts accept silently and reports reject with 8004da0c); and test the cascade headlessly by looping the runtime calls shown in the stepper above.

+Pros

  • Fully scriptable — provision many cascades or migrate in bulk; no Workstation editor gap.
  • Reproducible and version-controllable.
  • Identical runtime result to a Workstation-built chain.

−Cons

  • Developer effort — not a point-and-click path.
  • A couple of API traps to know (managed-attribute twins; the report filter shape).
  • You still design the same object chain — REST only creates it.

Build it

How to build it in Workstation

The point-and-click path for all three UI approaches. Nested prompts hit a well-known editor snag at step 3 — here's the full path, including the fix. The filter panel and hierarchy prompt are much simpler and follow after.

Nested prompts — the one with a catch

1

Create the level-1 prompt

Folder → New → Prompt → Elements of an attribute

Attribute: Category. Leave Filtered elements empty (level 1 shows everything). Set the title and instruction the user will read, tick Required, save as Elements of Category.

2

Wrap it in a filter

New → Filter → add qualification on Category → use a prompt

The filter's only condition is the prompt itself — qualification reads {Elements of Category}. Save as Category Filter Prompted. (You can also create the prompt inline here — Workstation then embeds it inside the filter; embedded and standalone prompts cascade identically.)

3

Create the level-2 prompt — and meet the gap

New → Prompt → Elements of an attribute → Subcategory → Filtered elements

The natural move is to point Filtered elements at Category Filter Prompted. Workstation refuses:

Error — New Untitled Prompt
The filter 'Category Filter Prompted' contains prompts. Filtered element browsing is not supported with a filter that contains prompts.

Why: the moment you pick a filter, the editor element-browses with it to show a preview. A prompted filter has no answer at design time, so the preview is impossible — and the editor rejects the pick instead of skipping the preview. This is an editor-preview limitation only. The engine resolves the restriction perfectly at run time (the live report in approach 1 is the proof), and the prompt object is allowed to reference a prompted filter.

4

The workaround: restrict by a placeholder, then swap

Filtered elements → pick a temporary static filter

Give the editor what it can preview: a throwaway static filter (say Category = Books). The preview works, the Subcategory prompt saves. Then edit that placeholder filter and replace its qualification with the Category prompt — exactly what you did in step 2. The prompt's stored restriction points at the filter object, so it now cascades. Server-verified: the swap commits and the reference survives.

Afterwards, don't reopen this prompt's Filtered elements picker — the preview shows the same harmless error; Cancel leaves the object intact. Quick sanity check instead: run the report; if the Subcategory list narrows to the chosen year, the link is live.

5

Wrap level 2, repeat for level 3

New → Filter → qualification = the Subcategory prompt

Save Subcategory Filter Prompted. Then repeat steps 3–5 for Item (placeholder → save prompt → swap placeholder to the Subcategory prompt → wrap in Item Filter Prompted). Stack as many levels as the business needs.

6

Put only the deepest filter on the report

Report editor → Filter panel → add existing filter → Item Filter Prompted

Template: Category, Subcategory, Item + Revenue. The engine discovers the whole chain from that one filter and asks the prompts in order — the sequential wizard you tried in approach 1.

Targeted filter panel

  1. Open a dashboard in edit mode and drag Category, Subcategory, Item from the dataset into the chapter's Filter panel.
  2. On the Category filter: More (…) → Select Targets → check Subcategory (and Item) → Apply. Repeat on Subcategory, targeting Item. (docs)
  3. Optionally check Update targets automatically so a downstream selection clears when its parent changes.

Hierarchy prompt

  1. New → Prompt → Hierarchy qualification ("qualify on a hierarchy"): pick the Products hierarchy, write the instruction, decide Required, save. No preview error here, because there's no filtered element browse involved.
  2. Add it to the report filter as a qualification. That's the whole chain — then optionally wrap the report in a dashboard.

Gotchas that matter

  • Make every level required. An optional lower prompt that goes unanswered means the report filter carries no qualification — nothing filters (KB37738). If you need optional levels, AND all the filters onto the report instead.
  • Keep cascade attributes related in the schema. Category → Subcategory → Item are parent–child in the Product hierarchy, so each restricted browse is a small lookup query. Unrelated attributes force fact-table joins per level — that's where nested prompts get slow.
  • Prompts are the "parameters." In classic Strategy BI there is no separate parameter object — a prompt is the reusable question, and its answer parameterizes the SQL.

Build it · legacy tool

Still using Developer (desktop)?

Developer's prompt editor has no preview restriction, so KB10434 works verbatim — no placeholder-swap needed:

  1. Prompt on Category's element list; save.
  2. Filter containing that prompt; save.
  3. Subcategory prompt: Use a filter to reduce the list of elements → pick the Category filter. Repeat for Item.
  4. Put the deepest filter on the report.

Same objects, same runtime as the Workstation or REST builds — don't reinstall Developer just for this; the placeholder swap or REST produce the identical graph.

Embedding Library in your own pages

Everything on this page is a plain <iframe> of Strategy Library — the same technique works in any intranet portal or web app. Four requirements make it reliable:

  • Allow embedding on the Library server. Library Admin → Library Server → Security Settings: allow embedding (list your portal's origins, or All for a demo environment) and set the cookies' SameSite attribute to None (Library then adds Secure). This demo environment is already configured.
  • Serve the hosting page from an http(s) origin. A page opened from disk (file://) has an opaque origin and browsers refuse to attach the session inside its frames.
  • Prefer same-domain hosting. On the same Tomcat/domain as Library the session cookie stays first-party — every browser works, including Safari. Cross-origin hosting works in Chrome and Edge with the SameSite setting above; Safari and third-party-cookie-blocked browsers need same-domain hosting or the Embedding SDK (embeddinglib.js).
  • Handle authentication. Viewers can sign in once inside any frame, or the page can pre-authenticate. This showcase auto-signs-in to a shared demo account for convenience — for production, prefer SSO/OIDC or the Embedding SDK over stored credentials.
